The next generation of REPL and Jupyter kernel for Go

gocell runs Go interactively — as a Jupyter kernel or a standalone REPL — by compiling every cell as a real Go plugin (-buildmode=plugin) loaded into one long-lived process. Variables, goroutines, and open connections persist in memory across cells: no interpreter, no re-execution.

Features

Everything below works identically in Jupyter and in gocell-repl — both are driven by the same session, which has no notion of which interface called it.

Goroutines that outlive a cell

A go func() { ... }() started in one cell keeps running in the background, fed from and read from independent later cells. A panic on one of these is recovered and reported to stderr instead of taking the whole kernel down with it — the opposite of Go's own default for a panic on any goroutine but the main one.

examples/live-goroutines.ipynb →

State persists with zero effort

No serialization, no %store-style magic: a variable's memory address is identical from cell to cell, because cells share the kernel process's own heap.

examples/heavy-model.ipynb →

Generics support

Type parameters work both within a cell and across cells, the same as any other type or function declaration.

examples/generics.ipynb →

Auto-import

A cell can use math.Sqrt(...) with no import "math" line at all — every cell runs through real goimports before building. Third-party packages resolve the same way, via a plain go build; set GOPROXY to control or restrict that.

Interruptible loops

Ctrl-C, SIGINT, or Jupyter's "Interrupt" button stops a stuck for/range loop without restarting the kernel. Background goroutines are left untouched.

Idempotent re-execution

:= becomes = when every left-hand name already exists, so re-running a cell doesn't hit Go's "no new variables" error. Combined with the plugin cache, re-running an unchanged cell is nearly free.

Auto-display

A bare last expression is captured and shown as the cell's result — like Jupyter's Out[n], or just printed in the REPL — instead of failing to compile.

Go 1.25+

Builds and runs against current Go toolchains. The kernel and every cell plugin share a toolchain version automatically.

Real compiled speed

Measured on an Apple M2, back to back, running examples/heavy-model.ipynb's exact workload (8M samples, 140 epochs of gradient descent) unmodified. One fit: gocell 1.46s, gophernotes 80.5s — about 20× — with both runs converging to the same result. gonb lands at 1.44s, essentially tied: it also compiles real Go, so raw CPU-bound speed isn't the difference.

The difference shows up over a session. gonb recompiles and reruns its whole accumulated program every cell, rather than keeping live state and goroutines in one process — so three consecutive cells (fit, then two more reading the result back) tell the real story.

Without explicitly reaching for gonb's own caching library, every cell that reads the fitted result silently reruns the entire fit — gonb has no persistent process to keep it in. Used correctly with gonb/cache, the gap nearly closes; gocell still comes out ahead with zero extra code.

How it works

Owned by session.Session, which doesn't depend on Jupyter or ZMQ — it drives the kernel and the REPL the same way. Shared state lives in a registry of unsafe.Pointers, so a later cell reads and writes through the original memory rather than a copy.

  1. 01

    ParseCell

    Splits imports, types, functions, statements.

  2. 02

    AnalyzeCell

    Resolves existing vs. new variables via go/types.

  3. 03

    GeneratePluginCode

    Writes the plugin's Go source, symbols rewired to shared pointers.

  4. 04

    BuildPlugin

    go build -buildmode=plugin, or a cache hit on the source hash.

  5. 05

    LoadAndExecute

    plugin.Open + Execute(ctx), recover()-guarded.

Known limitations
  • Memory never comes back down

    Go's plugin package can't unload a .so — roughly 1–1.4 MB of RSS per distinct cell. Only restarting the kernel reclaims it; structural to -buildmode=plugin.

  • No Windows support

    -buildmode=plugin isn't available there.

  • A background goroutine's output can land in an unrelated cell

    Capture redirects one shared file descriptor per cell, so a goroutine that prints during a later cell can be misattributed to it. The print itself is never corrupted or lost.

  • A new cell's first run includes compile time

    A fresh kernel to first hello world: 2446 ms cold, 1031 ms with Go's build cache warm (gonb 1386/811 ms, gophernotes — which interprets — 807/563 ms). Every later run of an unchanged cell is nearly free.
